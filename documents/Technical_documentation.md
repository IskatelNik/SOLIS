# ТЕХНИЧЕСКАЯ ДОКУМЕНТАЦИЯ (TDD) — Проект SOLIS

Данный документ описывает исчерпывающую техническую архитектуру, UI-дизайн и игровую логику для консольной игры **SOLIS** (C++17, SFML 3.0.2, nlohmann/json).

## 1. Архитектура и Базовый стек
* **Язык:** C++17
* **Фреймворк:** SFML 3.0.2 (Только для управления окном, рендера текста и базовых примитивов UI).
* **Работа с данными:** Библиотека `nlohmann/json`. **Data-Driven подход** — весь текст, враги, комнаты, лор и скиллы вынесены в JSON файлы, чтобы геймдизайнер мог менять баланс без перекомпиляции кода.
* **Паттерн управления:** State Machine (Конечный автомат). Игра всегда находится в одном из состояний: `MainMenu`, `HubState`, `ExplorationState`, `CombatState`, `GameOverState`.

## 2. Глобальные Менеджеры (Singleton или внедрение зависимостей)
* `Game`: Главный класс, владеет окном (`sf::RenderWindow`) и переключает Состояния.
* `ResourceManager`: Отвечает за загрузку и хранение шрифтов (`.ttf`) и парсинг текстовых файлов с ASCII-артами.
* `DataManager`: Загружает все базы данных при старте игры (`enemies.json`, `lore.json`, `skills.json`, `events.json`, `upgrades.json` и др.).
* `SaveManager`: Читает и перезаписывает `save.json` (мета-прогрессия, Искры Солиса, открытые Угли Мира, счетчики концовок, прогресс ивентов).
* `RunManager`: Хранит контекст текущего забега (какой сейчас уровень, текущие артефакты, временные Знания Мира, текущие ХП и Жар).

### 3. Архитектура UI (SFML Rendering)

Игра запускается в графическом окне (по умолчанию 1280x720), которое визуально имитирует текстовый терминал. Используется модульная система **UIBox** — прямоугольных зон (`sf::RectangleShape` для фона и границ), внутри которых отрисовывается динамический текст (`sf::Text`) и графические примитивы.

#### 3.1. Разметка экрана (Layout)

Экран разделен по горизонтали на три функциональные полосы.

**1. Информационная полоса (TopBar) — 10% высоты (72px):**

- **Локация (80% ширины):** Текстовый блок с названием текущей локации и сектора (например: _УРОВЕНЬ 2: Промзона | Сектор B-4_).
    
- **Режим (20% ширины):** Статус текущей активности игрока. Отображает контекст: «В БОЮ», «ИССЛЕДОВАНИЕ», «СОБЫТИЕ».
    

**2. Центральная полоса (MainDisplay) — 55% высоты (396px):**

- **Лог/Диалог (70% ширины):** Главное текстовое окно. Выводит описания комнат, результаты действий и реплики.
    
    - _Техническая реализация:_ Поддержка Word Wrap (автоперенос) и вертикальный скроллинг. История сообщений хранится в `std::list<std::string>`.
        
- **Визуал (30% ширины):** Окно для отрисовки ASCII-графики из внешних `.txt` файлов (изображения врагов или окружения).
    
    - _Нижняя часть блока:_ Вывод числового статуса цели (HP, активные баффы/дебаффы).
        

**3. Интерактивная полоса (ActionMenu) — 35% высоты (252px):**

- **Кнопки действий (70% ширины):** Динамический список вариантов выбора, привязанных к клавишам `[1]`, `[2]`, `[3]`, `[4]`.
    
    - _Вне боя:_ Навигация (переходы между комнатами) и выбор в сюжетных ивентах.
        
    - _В бою:_ Основные команды: `[1]` Атака, `[2]` Манипуляция, `[3]` Договориться.
        
- **Статус игрока (30% ширины):** Панель жизненных показателей.
    
    - **HP:** Текстовое и графическое отображение здоровья.
        
    - **Жар (HEAT):** Реализован в виде полосы (Progress Bar) с **цветовым градиентом от желтого к красному**. По мере накопления жара шкала заполняется, меняя цвет, что визуализирует критический перегрев систем.

## 4. Игровые Сущности и Классы

### 4.1. Player (Игрок)
* **Поля (Stats):** 
  * `int maxHp`, `int currentHp`
  * `float heat` (Жар, от 0.0 до 100.0+)
  * `int empathyLevel` (Уровень эмпатии для открытия черт врагов)
* **Экипировка:**
  * `std::vector<Skill*> activeSkills` (До 3-х штук).
  * `std::vector<Artifact*> artifacts` (Пассивные баффы).
* **Счетчики (на забег и глобальные):**
  * `int bloodCounter`, `int mercyCounter`, `int ideologyScore`.

### 4.2. Enemy (Враг)
* **Поля:** `string id`, `string name`, `string asciiArtPath`, `int maxHp`, `int currentHp`, `int baseDamage`, `int sparksReward`.
* **Черта (Trait):** Реализована через строго упорядоченный `enum class Trait`:
  `Fanatical = 0, Executive = 1, Mercenary = 2, Cynical = 3, Empathetic = 4, Cowardly = 5, Exhausted = 6, Embittered = 7`.
* **Статусы (Buffs/Debuffs):** `float damageModifier`, `float defenseModifier` (Меняются при механике «Отдать/Поглотить Жар»).

### 4.3. Локации (Rooms & Levels)
* `LevelModifier`: Структура с правилами для уровня (Например, `bool disableNeutralAnswers`, `float passiveCombatHeatRate`).
* `Room`: Класс, содержащий `string description`, вектор доступных переходов `std::vector<RoomOption>`, и тип события `EventType` (Бой, Лор, Сброс Жара, Ивент).

## 5. Алгоритм генерации карты и комнат (ExplorationState & RunManager)

Игра не использует двумерную сетку. Перемещение — это направленный граф (дерево выборов). За управление прогрессией отвечает `RunManager`.

### 5.1. Параметры Уровня (Биома)
Каждый уровень состоит из фиксированного количества «шагов» (комнат), например, 12 шагов.
*   `int currentRoomIndex = 0` (текущий шаг).
*   `int maxRoomsPerLevel = 12` (длина биома).
*   Когда `currentRoomIndex == maxRoomsPerLevel`, следующая комната жестко заменяется на Комнату Босса текущего уровня. После победы над боссом происходит переход на следующий уровень (`currentLevel++`).

### 5.2. Генерация развилки (Выбор дверей)
После завершения события в комнате (победа в бою, чтение лора), `ExplorationState` генерирует 2-3 варианта дальнейшего пути.
**Алгоритм:**
1.  Игра обращается к `rooms.json` и фильтрует массив `rooms`, оставляя только те комнаты, где `level == currentLevel`.
2.  Случайным образом выбираются 3 комнаты из отфильтрованного пула.
3.  Чтобы игрок мог делать осознанный выбор, в `rooms.json` каждая комната должна иметь поле `preview_text` (подсказка, которую игрок видит ДО входа в комнату).
4.  UI выводит варианты. Пример:
    *   `[1] Левая дверь (Слышен лязг металла и тяжелые шаги)` -> ведет в комнату типа `combat`.
    *   `[2] Вентиляция (Веет прохладой и озоном)` -> ведет в комнату `heat_sink`.
    *   `[3] Складская дверь (Пахнет старой бумагой)` -> ведет в `lore_room`.

### 5.3. Типы Комнат (Room Types) и их Механика
Каждая комната в `rooms.json` обязана иметь поле `"type"`. От этого поля зависит, как `ExplorationState` будет обрабатывать логику при входе.

#### 5.3.1. `combat` (Боевой патруль)
*   **Действие:** Мгновенный переход из `ExplorationState` в `CombatState`.
*   **Логика:** Игра парсит массив `possible_enemies`, спавнит одного врага, выдает ему черту и начинает бой. После победы игрок возвращается в `ExplorationState`, получает Искры и переходит к выбору следующей двери.

#### 5.3.2. `heat_sink` (Технический узел / Терминал)
*   **Действие:** Открывается интерактивное текстовое меню взаимодействия с окружением.
*   **Логика:** Игроку предлагается опция "Слить энергию". 
*   **Кнопки:** 
    *   `[1] Отдать 30% Жара` (Безопасно).
    *   `[2] Отдать 60% Жара` (Возможен риск урона или поломки, если предусмотрено балансом).
    *   `[3] Уйти`.
*   После использования терминал "сгорает" (опция блокируется), игрок идет к следующей развилке.

#### 5.3.3. `lore_room` (Архив / Лутовая)
*   **Действие:** Вывод нарративного текста и выдача награды.
*   **Логика:** Вызывается менеджер ресурсов. Игрок с вероятностью 50/50 получает:
    *   Либо **«Уголь Мира»** (Добавляется во временный инвентарь забега для диалогов. Игрок всегда находит лор которого у него нет и который доступен в это локации).
    *   Либо **Артефакт** (добавляется в массив `Player.artifacts`).

#### 5.3.4. `quest` (Сюжетный ивент)
*   **Действие:** Запуск скриптовой текстовой сцены с выборами (влияет на Идеологический компас, ХП или Жар). Детально описано в разделе 6.

## 6. Архитектура Сюжетных Ивентов (Комнаты `quest`)

В отличие от обычных боевых или лутовых комнат, которые генерируются случайно, сюжетные комнаты (ивенты) строго упорядочены, уникальны для каждого уровня (биома) и проходятся **только один раз за всю историю сохранений**. Для этого мы выносим их в отдельную базу данных `events.json`. Массив ивентов жестко отсортирован. В каждом ивенте есть ровно 2 выбора, которые всегда влияют на компас: один дает `+1` (путь Финесы / милосердие), другой `-1` (путь Фицио / радикализм).

### 6.1. Отслеживание Прогрессии
Чтобы игра понимала, на каком шаге сюжета находится игрок, в `save.json` добавляется объект `event_progress`. Он хранит индекс следующего не пройденного ивента для каждого биома.

### 6.2. Логика Генерации (Спавн Ивентов)
Модификация логики в `ExplorationState` при генерации 3-х дверей для игрока:
1.  Игра проверяет текущий уровень (например, `level_1`).
2.  Смотрит в `save.json` -> `event_progress["level_1"]`.
3.  Игра обращается к `events.json` и проверяет длину массива `"level_1"`.
4.  **Условие:** Если индекс меньше длины массива (ивенты еще не кончились), игра с шансом, например, **25%** генерирует одну из дверей как `quest`.
5.  В качестве текста двери (`preview_text`) берется строка из ивента под текущим индексом.
6.  Если индекс равен или больше длины массива (игрок прошел всю линейку сюжета в этом биоме), комнаты типа `quest` на этом уровне **больше никогда не генерируются** (заменяются на бои, терминалы или лор).

### 6.3. Обработка Выбора в Ивенте
Когда игрок заходит в комнату `quest` и нажимает `[1]` или `[2]`:
1.  К текущему `ideology_score` прибавляется `ideology_change` (всегда +1 или -1).
2.  К текущему Жару применяется `heat_change` (Ограничивается снизу нулем: `if (heat < 0) heat = 0`).
3.  Счетчик `event_progress[текущий_уровень]` увеличивается на `1`.
4.  Происходит мгновенное сохранение в `save.json`, чтобы игрок не мог перезапустить игру (Alt+F4) и перепройти ивент ради другой концовки.
5.  Генерируются следующие пути.

## 7. Спецификация Уровней и Модификаторов (RunManager)

В классе `RunManager` реализована логика смены биомов. Каждый уровень имеет жестко прописанные модификаторы, которые влияют на боевую и социальную системы.

### 7.1. Уровень 1: Камеры (Изолятор)
*   **Индекс уровня:** 1
*   **Описание:** Обучающий уровень, стандартные правила.
*   **Пул комнат:** `level == 1` из `rooms.json`.
*   **Модификаторы:** Отсутствуют. Базовое получение Жара, 4 варианта ответа в диалогах (1 верный, 1 нейтральный, 2 неверных).

### 7.2. Уровень 2: Мануфактуры (Промзона)
*   **Индекс уровня:** 2
*   **Описание:** Упор на менеджмент Жара. Враги "заряжены".
*   **Модификаторы:**
    1.  **Отключение нейтралитета:** В функции генерации диалога слот "Нейтральный" заменяется на "Неверный". Вариантов ответа становится 3 (1 верный, 2 неверных). Если генерируется 4-я кнопка, она тоже неверная.
    2.  **Overcharged Enemies:** При старте боя у всех врагов `defenseModifier` изначально повышен на `0.2f`. Игроку *выгодно* использовать "Поглотить энергию", чтобы снять этот бафф.
    3.  **Генерация комнат:** Вероятность выпадения комнаты типа `heat_sink` (Сброс Жара) увеличена на 30%.

### 7.3. Уровень 3: Исследовательские (Лаборатории)
*   **Индекс уровня:** 3
*   **Описание:** Место экспериментов, хаос в артефактах и жесткие наказания за ошибки в диалогах.
*   **Модификаторы:**
    1.  **Штраф за диалог:** Если в социальном бою игрок выбирает "Неверный" вариант ответа, помимо баффа врага, игрок получает пенальти: `Player.heat += 15.0f`.
    2.  **Нестабильность Артефактов:** Каждые 3 комнаты вызывается функция `ShuffleArtifact()`. Один случайный артефакт в инвентаре игрока заменяется на другой случайный артефакт из пула.

### 7.4. Уровень 4: Печь
*   **Индекс уровня:** 4
*   **Описание:** Финальный рывок. Жар убивает игрока сам по себе.
*   **Модификаторы:**
    1.  **Пассивный нагрев:** В `CombatState`, в начале каждого хода (перед тем как игрок сделает выбор), автоматически применяется `Player.heat += 10.0f`.

## 8. Генерация Врагов и Механика Боссов

### 8.1. Спавн обычных врагов
Когда игрок выбирает комнату типа `combat`, `RunManager` смотрит массив `possible_enemies` этой комнаты.
1.  Случайным образом выбирается ID врага (например, `"enemy_guard"`).
2.  Вызывается `Enemy::Spawn("enemy_guard")`.
3.  Врагу присваивается случайная черта (Trait) из его личного пула `possible_traits`. Выводится соответствующий `intro_text`.

### 8.2. Алгоритм Социального Боя с Боссом

Класс `BossEnemy` (наследник `Enemy`) должен отслеживать текущую фазу на основе `currentWillpower`.

1.  **Начало фазы Диалога:** В лог боя выводится `boss_replica` текущей фазы (например, фазы, где `willpower_left == 3`).
2.  **Генерация ответов:** Когда игрок нажимает "Договориться", `DialogueGenerator` использует не базовую черту босса (которой нет), а `target_trait` из **текущей фазы**. То есть для генерации 4-х кнопок ответов игра ищет Лор, подходящий именно к этой реплике.
3.  **Выбор Игрока:**
    *   **Верный ответ:** 
        *   В лог выводится `success_reply`. 
        *   `currentWillpower--`. 
        *   Жар игрока снижается (напр., на 20%), чтобы поощрить правильный выбор.
        *   Босс переходит в статус `Aggression` на количество ходов, равное `aggression_turns` (кнопка "Договориться" блокируется, игрок вынужден защищаться/лечиться).
    *   **Неверный/Нейтральный ответ:** 
        *   В лог выводится `fail_reply`. 
        *   Босс получает бафф урона и немедленно атакует. Воля не снимается. Игроку придется пытаться снова на следующем ходу.
4.  **Конец Агрессии:** Когда счетчик `aggression_turns` доходит до 0, босс возвращается в фазу Диалога. В лог выводится `boss_replica` для следующей фазы (где `willpower_left == 2`). Цикл повторяется.

## 9. Логика Систем

### 9.1. Боевая система (Turn-Based Loop)
Бой происходит в `CombatState`. 
* **Ход игрока:**
  1. Выбор "Атака" -> Открытие подменю -> Выбор скилла -> Вызов `Skill.Use(Player, Enemy)` -> Расчет урона и добавление Жара.
  2. Выбор "Манипуляция" -> Поглотить (Дебафф врага, +Жар) / Отдать (Проверка `if(heat > 0)`, Бафф врага, -Жар, +ХП в зависимости от количества отданного Жара).
  3. Выбор "Договориться" -> Переход в подменю Социального боя.
* **Ход врага:**
  1. Вызов `Enemy.Attack(Player)`.
  2. Триггер модификаторов уровня (Например, на 4 уровне: `Player.heat += 10.0f`).
  3. Проверка статуса "Перегрузка" (Если `heat > 85.0f` -> `Player.currentHp -= overloadDamage`).

### 9.2. Социальная система (Генератор Диалогов)
Функция генерации 4-х вариантов ответа при нажатии «Договориться»:
1.  Определить индекс черты текущего врага (`target_i`).
2.  Создать пул из 4 слотов: `Option[4]`.
3.  **Слот 1 (Верный):** Искать в базе открытых игроком "Углей Мира" элемент, привязанный к `target_i`. Если найдено -> вставить. Если нет -> вставить фразу-заглушку `Placeholder_Wrong` (с пометкой "Неверно").
4.  **Слот 2 (Нейтральный):** Искать лор для индексов `target_i-1` или `target_i+1`. Если уровень = 2 (Промзона), этот слот заменяется на **Неверный**. Если не найдено -> вставить `Placeholder_Wrong`.
5.  **Слоты 3 и 4 (Неверные):** Заполнить случайным лором из остальных 5 индексов, либо фейковыми фразами-заглушками `Placeholder_Wrong`.
6.  **Перемешивание:** Применить `std::shuffle` к массиву слотов, чтобы правильный ответ оказался на случайной кнопке (от 1 до 4). Вывести на экран.

### 9.3. Влияние на Социальный бой
Важное уточнение для генератора диалогов (`DialogueGenerator`):
Пул доступных ответов для игрока формируется ИЗ ВСЕХ найденных кусков лора за все время игры (`unlocked_lore`), **независимо от текущего уровня**.
*Пример:* Игрок на 3-м уровне (Лаборатории) может использовать Лор, найденный на 1-м уровне (Тюрьма), если этот лор бьет точно в Черту текущего врага. Мета-знания персонажа не имеют границ между уровнями.

### 9.4. Алгоритм Эмпатии
*   Изначально UI скрывает имя черты врага (выводит `Черта: ???`).
*   У игрока есть скрытый стат `empathyLevel = 0`.
*   За выбор Верного ответа в соц. бою: `empathyLevel += 10`. За Неверный: `empathyLevel += 2`.
*   Если `empathyLevel >= ENEMY_EMPATHY_THRESHOLD`, текст `???` заменяется на реальное название черты.

## 10. Экономика Искр и Мета-Прогрессия Хаба

### 10.1. Заработок валюты («Искры Солиса»)
Валюта добывается исключительно в `CombatState`. В файле `enemies.json` каждому врагу (и боссу) добавлено поле `"sparks_reward"`.
*   **При убийстве (ХП врага = 0):** Игрок гарантированно получает указанное количество Искр.
*   **При Социальной победе (Воля/Диалог):** Игрок также получает Искры (чтобы не наказывать пацифистов отсутствием прокачки), плюс получает временный бафф на забег.
*   В момент победы вызывается `SaveManager::AddSparks(amount)`, который мгновенно перезаписывает текущий баланс в файл `save.json`, чтобы при случайном вылете валюта не пропала.

### 10.2. Архитектура Дерева Прокачки (`upgrades.json`)
Временные баффы хранятся в `artifacts.json` (теряются при смерти). А вот перманентная прокачка в Хабе хранится в отдельном файле — `upgrades.json`.
Апгрейды делятся на два типа:
1.  `active_skill` — новые заклинания для боя.
2.  `passive_stat` — перманентные улучшения тела героя (базовые статы).

### 10.3. Логика Хаба (`HubState`)
Когда игрок умирает, `RunManager` обнуляет его временный инвентарь и переводит игру в `HubState` (Очаг Предков). Здесь открывается меню прокачки и подготовки к новому забегу.
*   **Магазин Прокачки:**
    *   UI читает `upgrades.json` и выводит список апгрейдов.
    *   Игра проверяет `save.json`. Если ID апгрейда уже есть в массиве `unlocked_upgrades`, он помечается как `[КУПЛЕНО]` и блокируется для покупки.
    *   Если у игрока хватает Искр, он покупает апгрейд: Искры списываются из `save.json`, а ID апгрейда добавляется в `unlocked_upgrades`.
*   **Сборка Билда (Экипировка перед забегом):**
    *   В Хабе есть меню "Экипировка". Оно выводит все `active_skill`, которые куплены игроком.
    *   Игрок выбирает до 3-х навыков. Эти навыки записываются в `save.json` в отдельный массив `equipped_skills`. (Это нужно, чтобы при перезаходе в игру билд не сбрасывался).

### 10.4. Инициализация Нового Забега (`RunManager::StartNewRun()`)
Это критически важный момент. Когда игрок нажимает "Начать забег" и выходит из Хаба, игра должна правильно «собрать» базовые статы игрока.
**Алгоритм (Порядок загрузки статов):**
1.  Инициализировать `Player` базовыми константами (например, `MaxHP = 100`, `OverloadThreshold = 85.0`).
2.  Считать `save.json` -> `unlocked_upgrades`.
3.  Для каждого купленного апгрейда проверить его `type` в `upgrades.json`.
4.  Если это `passive_stat`, применить математику К БАЗОВЫМ СТАТАМ.
    *   *Пример:* Куплено 2 прокачки ХП по +10. `Player.maxHp = 100 + 20 = 120`. `Player.currentHp = 120`.
5.  Считать `save.json` -> `equipped_skills`.
6.  Считать из `skills.json` данные об этих 3-х навыках и загрузить их в `Player.activeSkills`. (Теперь в бою при нажатии "Атака" будут выводиться именно они).
7.  Запустить `ExplorationState` (Уровень 1, Комната 1).

## 11. Архитектура Артефактов (Пассивные баффы)

Артефакты (лут на один забег) не должны хардкодиться. Они парсятся из `artifacts.json` и используют систему **Модификаторов (Modifiers)**, которые перехватывают события в коде (Hooks).

### 11.1. Логика применения в коде
Когда игра хочет рассчитать получаемый Жар, она не просто берет базовое число, а прогоняет его через все артефакты игрока:
```cpp
float Player::CalculateHeatGain(float baseHeat) {
    float finalHeat = baseHeat;
    for (auto& artifact : artifacts) {
        if (artifact.effect_type == "heat_reduction_multiplier") {
            finalHeat *= artifact.effect_value; // Например, 0.8 (снижение на 20%)
        }
    }
    return finalHeat;
}
```

## 12. Расширенная механика Навыков (Заклинания)

Навыки (Skills) из Хаба — это не просто `Damage + Heat`. Они могут накладывать статусные эффекты на врага, лечить игрока или взаимодействовать со скрытыми механиками (например, временно понижать баффы от перегрузки врага).

### 12.1. Эффекты (Effects System)
Каждый навык в `skills.json` должен содержать массив `effects`, который парсится боевой системой (`CombatSystem`).

### 12.2. Обработка Ходов (Turn Manager)
Чтобы временные эффекты (напр. снижение урона врага на 2 хода) работали, класс `Enemy` должен иметь список активных эффектов `std::vector<StatusEffect> activeEffects`.
В конце каждого хода врага (`EndTurn`), `CombatState` проходит по этому списку, уменьшает `duration_turns` на 1. Если `duration_turns == 0`, эффект удаляется, а статы врага возвращаются в норму.

## 13. Алгоритм генерации «Углей Мира»

### 13.1. Логика Лутовой Комнаты (Архив / `lore_room`)
Когда игрок входит в `lore_room`, игра вызывает функцию генерации награды `GenerateRoomLoot()`. Эта функция должна проверять файл сохранений и фильтровать базы данных.

#### 13.1.1. Алгоритм выборки Лора:
1.  **Сбор доступного пула:** Игра обращается к `lore.json` и собирает список всех кусков лора, у которых `level == currentLevel`.
2.  **Фильтрация дубликатов:** Из этого пула удаляются все `id`, которые УЖЕ записаны в `save.json` в массиве `unlocked_lore`.
3.  **Определение пустой базы:** 
    *   Если после фильтрации пул **пуст** (игрок нашел все записки в этом биоме за прошлые забеги), шанс выпадения Артефакта становится **100%**.
4.  **Стандартный ролл (если база не пуста):**
    *   Игра бросает кубик (например, 50% шанс на Лор, 50% шанс на Артефакт).
    *   *Если выпал Лор:* Случайным образом выбирается один из оставшихся кусков лора.

#### 13.1.2. Обработка поднятия Лора:
*   Отображается `pickup_text`.
*   ID лора немедленно добавляется в список `unlocked_lore` в `save.json` (сохраняется навсегда).
*   Этот лор становится доступен для Социального боя (генератора диалогов) уже в следующем бою этого же забега, а также во всех будущих забегах.
*   *В коде для ИИ это должно выглядеть примерно так:*
```cpp
// ПСЕВДОКОД ДЛЯ ИИ-АГЕНТА
std::vector<LoreItem> availableLore;
for (const auto& lore : AllLoreDatabase) {
    if (lore.level == currentLevel && !SaveManager::IsLoreUnlocked(lore.id)) {
        availableLore.push_back(lore);
    }
}

if (availableLore.empty()) {
    // В биоме больше нет нового лора! Форсируем выдачу Артефакта.
    GiveRandomArtifact();
} else {
    // Стандартная рулетка
    if (Random::Float(0.0f, 1.0f) > 0.5f) {
        LoreItem droppedLore = GetRandomLore(availableLore);
        SaveManager::UnlockLore(droppedLore.id);
        ShowLootScreen(droppedLore.pickup_text);
    } else {
        GiveRandomArtifact();
    }
}
```

## 14. Скрытые триггеры и Логика Концовок

За концовки отвечают три переменные, которые хранятся в `RunManager` во время забега и обновляются в `SaveManager`.

### 14.1. Обновление Счетчиков
*   `blood_counter` (Счетчик Крови): `+1` за каждого убитого врага (ХП = 0).
*   `mercy_counter` (Счетчик Милосердия): `+1` за каждого врага, побежденного через Социальный бой (кнопка "Договориться").
*   `ideology_score` (Идеологический компас): Изменяется в сюжетных текстовых ивентах (комнаты типа `quest`).
    *   Ответы в поддержку Фицио (радикальные): `-1`.
    *   Ответы в поддержку Финесы (идеи отца): `+1`.

### 14.2. Алгоритм выбора Концовки (Конец 4-го уровня)
После победы над финальным боссом (Виндикт), игра переходит в `EndingState`. Там запускается функция `DetermineEnding()`, которая жестко следует этим правилам (порядок проверок важен):

```cpp
// ПСЕВДОКОД ДЛЯ ИИ-АГЕНТА

if (mercy_counter >= REQUIRED_MERCY_FOR_TRUE && blood_counter == 0 && AllLoreUnlocked()) {
    // 1. ИСТИННАЯ КОНЦОВКА
    // Триггер: Идеальное пацифистское прохождение, полная Энциклопедия, Виндикт побежден социально.
    PlayEnding("true_ending");
} 
else if (blood_counter > mercy_counter && ideology_score < 0) {
    // 2. КОНЦОВКА ФИЦИО
    // Триггер: Доминация убийств и поддержка радикальных идей (отрицательный компас).
    PlayEnding("ficio_ending");
} 
else if (mercy_counter > blood_counter && ideology_score > 0) {
    // 3. КОНЦОВКА ФИНЕСЫ (Ф)
    // Триггер: Доминация милосердия и поддержка идей отца (положительный компас).
    PlayEnding("finesa_ending");
} 
else {
    // 4. НЕЙТРАЛЬНАЯ КОНЦОВКА
    // Триггер: Fallback (все остальные случаи). Смешанный стиль, игнорирование идеологии.
    PlayEnding("neutral_ending");
}
```

## 15. Математика и Формулы

### 15.1. Игрок (Player)
*   **Жар (Heat):** Значение `float` от `0.0` до `100.0` (и выше при перегреве).
*   **Перегрузка:** Если в конце хода `heat > 85.0`, игрок получает урон: `damage = (heat - 85.0) * OVERLOAD_MULTIPLIER` (например, множитель 0.5).
*   **Самовозгорание:** Если при входе в `StateCombat` (начало боя) `heat >= 100.0` -> Мгновенная смерть (переход в `GameOverState`).

### 15.2. Манипуляция энергией (Действия в бою)
*   **Поглотить (Take Energy):** 
    *   `Player.heat += BASE_TAKE_HEAT` (напр. +15%).
    *   `Enemy.defenseModifier -= 0.2f` (Дебафф брони врага на 20%).
*   **Отдать (Give Energy):**
    *   **Условие:** Доступно только если `Player.heat > 0`. Игрок отдает весь жар или фиксированную порцию (напр. 20%).
    *   `Player.heat -= GIVEN_HEAT`.
    *   `Player.currentHp += (GIVEN_HEAT * HEAL_MULTIPLIER)`.
    *   `Enemy.damageModifier += 0.2f` (Бафф урона врага на 20%).

### 15.3. Социальный Бой и Кольцо Черт
Черты врагов (Traits) программно реализованы как массив из 8 элементов со строгим порядком:
`[0] Fanatical -> [1] Executive -> [2] Mercenary -> [3] Cynical -> [4] Empathetic -> [5] Cowardly -> [6] Exhausted -> [7] Embittered`.

*   **Идентификация соседей:** Если черта врага имеет индекс `i`:
    *   Верный ответ: Индекс `i`.
    *   Нейтральный ответ: Индексы `(i - 1 + 8) % 8` и `(i + 1) % 8`.
    *   Неверный ответ: Все остальные индексы.

### 15.4. Формула Урона (Skills)
Урон навыков масштабируется от текущего уровня Жара игрока. Расчет происходит ДО того, как навык прибавит свой собственный Жар.
*   **Множитель Жара:** `float heatMultiplier = 1.0f + (Player.heat / 100.0f);` (от 1.0 до 2.0+).
*   **Итоговый урон:** `float finalDamage = skill.base_damage * heatMultiplier * Enemy.defenseModifier;`

## 17. Жизненный цикл (State Machine Flow)
1.  `Init`: Запуск `main.cpp`, загрузка шрифтов в `ResourceManager`, парсинг `.json` файлов в `DataManager`.
2.  `MainMenuState`: Отрисовка названия игры "SOLIS". Кнопка "Начать забег".
3.  `HubState` (Очаг Предков): Игрок читает `save.json`. Тратит искры. Собирает билд. Нажимает "Спуститься".
4.  `ExplorationState`: Загрузка пула комнат для Уровня 1.
    *   Игрок читает лор -> Нажимает [1] (Идти дальше).
    *   Система генерирует следующую комнату. Если комната боевая -> Переход в `CombatState`.
5.  `CombatState`:
    *   Пошаговый цикл. Ход игрока -> Ход врага.
    *   Победа -> Начисление Искр, возврат в `ExplorationState`.
    *   Смерть (от ХП или Перегрева) -> Запись накопленных ресурсов в `save.json`, очистка инвентаря забега, переход в `HubState`.
